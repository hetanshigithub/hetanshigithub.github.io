Hookshot

Webhook delivery service

A service that delivers webhooks and does not lose or repeat them. Workers claim deliveries with FOR UPDATE SKIP LOCKED and a lease, so a worker that dies does not hold a job forever. Failed deliveries retry with jittered exponential backoff and end up in a dead-letter queue. Every payload is signed with HMAC-SHA256, requests carry idempotency keys, and outgoing calls are guarded against SSRF.

I injected the clock so timing logic can be tested exactly. The claim test above runs against H2 and PostgreSQL 16 in CI, because a concurrency test that passes on the wrong database proves very little.

Case study: making sure nothing is claimed twice
Problem
Webhook systems fail quietly. An event gets delivered twice, never delivered, or sent somewhere it should not go. Every one of those is hard to see afterward.
My role
I built it on my own: the design, the Java backend, the database layer, the tests and the CI.
Decisions
Claim rows with FOR UPDATE SKIP LOCKED and a lease, so a crashed worker releases its job. Retry with jittered exponential backoff, then a dead-letter queue. Sign payloads with HMAC-SHA256 and use idempotency keys. Inject the clock so timing logic can be tested exactly. Run CI on both H2 and PostgreSQL 16.
Result
ConcurrentClaimTest has 8 workers compete for 200 deliveries, and none is claimed twice. It passes on PostgreSQL 16 in CI.

Retrieval service

The index rebuilds itself when the documents change, so old data cannot slip into results. A lightweight offline embedder lets tests and CI run without downloading a model.

Case study: search that can show its work
Problem
Document search goes wrong in two quiet ways: the index is out of date, or nobody measures whether the answers are any good.
My role
I built the whole service on my own, from ingestion to the API and the tests.
Decisions
Give the document set a fingerprint and rebuild the index when it changes. Pair the sentence-transformer model with a small offline embedder, so tests and CI run without downloading a model. Pull answers from the source text and do not generate them. Score the system on a fixed question set.
Result
A 37-question evaluation set scored with recall@k, MRR and groundedness, plus 58 automated tests across ingestion, retrieval and the API.
